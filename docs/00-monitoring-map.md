# 00. Карта мониторинга

## 1. Зачем нужна карта, а не список слов

Поиск по словам «Wildberries» и «Ozon» возвращает поток, в котором нужное составляет доли процента: подборки товаров, скидки, пресс-релизы, мотивационные посты и пересказы чужих пересказов. Отфильтровать это словами нельзя — в каждом из них те же слова.

Карта решает другую задачу. Она описывает **пространство наблюдения** по четырём осям и для каждой точки этого пространства отвечает на три вопроса: почему это нас касается, как это обнаруживается, во что это превращается на выходе.

| Ось | Что описывает | Где хранится машиночитаемо |
|---|---|---|
| **Площадки** | Кого мониторим и с каким приоритетом | `config/monitoring-map.yaml` → `platforms` |
| **Темы** | Что именно отслеживаем внутри площадки | `config/monitoring-map.yaml` → `topics` |
| **Сигналы** | То, что не является новостью, но требует внимания | `config/monitoring-map.yaml` → `signals` |
| **Стоп-лист** | Что отбрасывается детерминированно, до всякой оценки | `config/triage.yaml` → `stop_rules` |

Пятая сущность — **группы запросов** (`config/queries.yaml`) — не ось, а инструмент: конкретные строки, которыми оси прочёсываются.

**Главный вопрос, на который обязан отвечать любой материал:**

> Селлер прочитал это — он заработает, не потеряет деньги, избежит риска или быстрее примет решение?

Если «нет» — материал не идёт дальше, сколько бы баллов он ни набрал по формальным признакам.

### 2.2. Важная оговорка про эти числа

**Приоритет площадки — это тай-брейк очереди, а не баллы матрицы.**

В матрице оценки (§9 ТЗ, реализована в [01-triage-scoring.md](01-triage-scoring.md)) есть ровно один платформенный фактор: `platform_wb` = +25. Значений для Ozon, Яндекс Маркета и второго эшелона в матрице нет, и я их туда **не добавляю** — иначе сумма перестанет соответствовать порогам 80/60/40, которые заданы под исходный набор весов.

Числа 15 / 10 / 5 из таблицы выше работают иначе: при **равной сумме баллов** первым в очередь идёт материал по более приоритетной площадке. Это влияет на порядок работы, но не на то, попал ли материал в полосу `URGENT`, `QUEUE` или `BACKLOG`.

**Чем платим.** Событие на Ozon, идентичное по последствиям событию на WB, наберёт на 25 баллов меньше и может уйти на полосу ниже. Это сознательный перекос: канал про WB в первую очередь, и матрица из ТЗ его прямо закрепляет.

### 2.3. Порог входа для P4

Площадки четвёртого приоритета попадают в работу не по факту упоминания, а только при одном из условий:

- значимая инновация, применимая к селлерам других площадок;
- скандал, расследование, утечка;
- регуляторная или судебная история;
- кейс, из которого следует практический вывод;
- рыночное движение: уход, приход, слияние, смена модели.

Обычная операционная новость P4-площадки («Hoff расширил ассортимент») отбрасывается стоп-правилом `STOP_TOO_GENERAL`.

**Почему порог.** Тринадцать дополнительных площадок при обычном режиме дают больше шума, чем три основные вместе взятые, а плотность полезного у них ниже на порядок. Без порога входа расширение охвата ухудшает канал, а не улучшает.

## 4. Ось «Сигналы»

Сигнал — это то, что **не является новостью**, но означает, что что-то произошло. Классический мониторинг его пропускает, потому что ищет публикации, а сигнал часто существует только как изменение состояния.

| Сигнал | Как обнаруживается | Метод |
|---|---|---|
| Важные изменения в документах маркетплейсов | Сравнение снапшотов оферты и тарифов | `doc_diff` |
| Массовые жалобы селлеров | Всплеск независимых упоминаний одной проблемы в окне | `mass_detector` |
| Обсуждения новых штрафов или удержаний | То же, с фильтром по формулировке основания | `mass_detector` |
| Резкие изменения рекламных ставок | Отклонение метрики от скользящего среднего | `metric_jump` |
| Новые инструменты в личных кабинетах | Diff снапшота интерфейса и справки | `cabinet_snapshot_diff` |
| Исчезновение или появление функций | То же | `cabinet_snapshot_diff` |
| Новые ограничения в категориях товаров | Diff справочных разделов | `doc_diff` |
| Крупные кейсы селлеров | Отбор редактора и подтверждение | `editorial_pick` |
| Аналитические отчёты | Появление публикации в отслеживаемом реестре | `registry_watch` |
| Судебные документы | Новая запись в картотеке по списку ИНН | `registry_watch` |
| Заявления регуляторов | Новая запись в разделе ведомства | `registry_watch` |
| Новые AI-сервисы | Появление в отслеживаемых источниках | `registry_watch` |
| Исследования рынка | То же | `registry_watch` |
| Финансовые отчёты маркетплейсов | Раскрытие эмитента, IR-раздел | `registry_watch` |
| Изменения в поведении покупателей | Отклонение метрики | `metric_jump` |
| Сезонные аномалии спроса | Отклонение от сезонной нормы | `metric_jump` |
| Технологические обновления платформ | Diff changelog'а и спецификации API | `api_changelog_diff` |
| Заметные конфликты и скандалы | Всплеск упоминаний + подтверждение | `mass_detector` |

**Почему сигналы вынесены в отдельную ось.** Самая ценная фактура — тихая правка справки или новое поле в API — не сопровождается ни одной публикацией. Если мониторить только тексты, такое событие приходит к нам через несколько дней в чужом пересказе. Diff состояния даёт его в момент появления.

**Чем платим.** Diff шумит: площадки правят вёрстку, переставляют блоки, меняют формулировки без смысловых последствий. Поэтому сигнал типа `doc_diff` — это всегда кандидат на проверку, а не готовое событие: он входит в очередь, но не может сам по себе стать материалом.

## 5. Ось «Стоп-лист»

Четырнадцать правил из §8 ТЗ. Они срабатывают **до подсчёта баллов** — см. обоснование в [01-triage-scoring.md](01-triage-scoring.md) §4.

| Код | Что отбрасывает |
|---|---|
| `STOP_PR_RELEASE` | Мелкие рекламные пресс-релизы без пользы для селлеров |
| `STOP_PRODUCT_ROUNDUP` | Подборки товаров |
| `STOP_DISCOUNT_NOISE` | Скидки и распродажи без рыночного значения |
| `STOP_MINOR_PROMO` | «Маркетплейс запустил маленькую акцию» |

| `STOP_UNCONFIRMED_RUMOR` | Слухи без указания источника вообще |
| `STOP_RETELLING` | Пересказ без нового факта |
| `STOP_OLD_NEWS` | Старые новости |
| `STOP_DUPLICATE` | Дубли одной и той же темы |
| `STOP_BUYER_ONLY` | Касается только покупателей, не влияет на продавцов, рынок и правила |
| `STOP_TOO_GENERAL` | Слишком общие статьи без конкретики |
| `STOP_MOTIVATIONAL` | Мотивационные посты без фактов |
| `STOP_OPINION_NO_DATA` | Личные мнения без данных |
| `STOP_NO_SOURCE` | Невозможно проверить источник |

### 5.1. Разграничение `STOP_UNCONFIRMED_RUMOR` и фактора «нет подтверждения»

Два механизма выглядят одинаково и означают разное. Без явной границы они конфликтуют.

| | `STOP_UNCONFIRMED_RUMOR` (стоп-правило) | `no_confirmation` (−50 в матрице) |
|---|---|---|
| Когда | Источник не назван вообще: «говорят, что», «по слухам» | Источник назван и идентифицируем, но независимого подтверждения пока нет |
| Что происходит | Отбрасывается, до матрицы не доходит | Считается, теряет 50 баллов, обычно уходит в `BACKLOG` |
| Почему так | Проверять нечего — нет объекта проверки | Проверять есть что; подтверждение может появиться позже |

Второй случай важен: именно так выглядит ранний сигнал о массовом сбое. Отбросить его вместе со слухами — потерять самое ценное по времени. Поэтому он живёт в `BACKLOG` с механизмом подъёма при появлении подтверждения.

### 5.2. Отсев сохраняется

Каждое срабатывание стоп-правила пишется в `stop_rule_drops` с кодом причины и ссылкой на материал. Без этого невозможно померить, сколько нужного выброшено: правило, которое молча ест 3% полезного потока, выглядит как отсутствие новостей.

**27 августа 2026** охват сознательно расширен за пределы трёх основных площадок: добавлены тринадцать площадок P4, а также темы AI, трендов рынка и потребительского поведения.
