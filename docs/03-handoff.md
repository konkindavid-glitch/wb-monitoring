# 03. Контракт передачи и граница модуля

## 1. Где модуль заканчивается

Карта мониторинга отдаёт наружу **приоритизированную очередь находок с разбором оценки**. Она не проверяет факты, не пишет тексты и не решает, публиковать ли.

```
┌─ КАРТА МОНИТОРИНГА (этот модуль) ─────────────────────────┐
│  источники → находка → стоп-правила → матрица             │
│            → triage_decision → очередь                    │
└──────────────────────────┬────────────────────────────────┘
                           │  hit.schema.json
                           ▼
┌─ DOWNSTREAM (вне модуля) ─────────────────────────────────┐
│  фактчекинг → четыре гейта → написание → модерация        │
└───────────────────────────────────────────────────────────┘
```

Граница выбрана по месту, где меняется природа работы: слева — отбор и приоритизация по формальным признакам, справа — проверка утверждений и редакционное решение. Смешивать их в одном модуле означает получить оценку важности, зависящую от того, насколько удачно прошёл фактчекинг, — и потерять возможность калибровать одно, не трогая другое.

## 2. Что уходит наружу

Полная схема — [`schemas/hit.schema.json`](../schemas/hit.schema.json). Пример находки:

```json
{
  "hit_id": "hit_01J9XQ2M4K7T",
  "discovered_at": "2026-08-27T09:14:22Z",
  "published_at": "2026-08-27T09:08:00Z",
  "url": "https://seller.wildberries.ru/.../tariffs",
  "title": "Изменение тарифов хранения с 3 сентября",
  "excerpt": "Коэффициент хранения для категории ... повышается с ...",
  "platforms": ["WILDBERRIES"],
  "topics": ["seller_money", "logistics_warehouse"],
  "categories": ["COMMISSION_TARIFF", "LOGISTICS"],
  "signal": "doc_change",
  "source_ref": {
    "source_key": "wb_tariffs_page",
    "tier": "T1",
    "snapshot_id": "snap_01J9XQ1..."
  },
  "score": 130,
  "factors": {
    "platform_wb":            {"hit": true, "weight": 25, "why": "раздел тарифов WB"},
    "seller_money_impact":    {"hit": true, "weight": 25, "why": "прямые расходы на хранение"},
    "rules_change":           {"hit": true, "weight": 20, "why": "новая редакция тарифной таблицы"},
    "authoritative_source":   {"hit": true, "weight": 15, "why": "официальный раздел площадки"},
    "is_fresh":               {"hit": true, "weight": 15, "why": "обнаружено через 6 минут"},
    "has_practical_takeaway": {"hit": true, "weight": 15, "why": "пересчёт себестоимости хранения"},
    "mass_effect":            {"hit": true, "weight": 15, "why": "затронуты все FBO-поставки"},
    "ai_link":                {"hit": false, "weight": 0},
    "legal_tax_risk":         {"hit": false, "weight": 0},
    "has_conflict":           {"hit": false, "weight": 0},
    "is_repeat":              {"hit": false, "weight": 0},
    "is_old":                 {"hit": false, "weight": 0},
    "no_confirmation":        {"hit": false, "weight": 0},
    "is_advertising":         {"hit": false, "weight": 0}
  },
  "triage_decision": "URGENT",
  "effective_date": "2026-09-03",
  "state": "TRIAGED"
}
```

### 2.1. Обязательные поля и почему они обязательны

| Поле | Почему обязательно |
|---|---|
| `factors` целиком, все 14 | Позволяет пересчитать находку при перекалибровке весов без повторного прохода |
| `why` у каждого сработавшего фактора | Фактор без обоснования не засчитывается — защита от «вроде влияет на деньги» |
| `source_ref` | Без ссылки на источник находка непроверяема, а значит бесполезна downstream |
| `discovered_at` и `published_at` раздельно | Свежесть считается от момента, когда информация стала доступна, а не когда произошло событие |
| `triage_decision` | Единственное решение, которое модуль принимает и за которое отвечает |

`effective_date` не обязателен, но если он извлечён — передаётся: downstream строит по нему календарь напоминаний, а внутри модуля он работает тай-брейком очереди.

## 3. Четыре гейта как внешний интерфейс

Модуль ни один из четырёх гейтов не считает. Они описаны здесь, чтобы решение «матрица определяет приоритет, а не публикацию» было выразимо внутри автономного проекта и чтобы стыковка с downstream не требовала догадок.

```
PUBLISH ⟺ importance    ≥ I_min
        ∧ confidence    ≥ C_min
        ∧ novelty       ≥ N_min
        ∧ actionability ≥ A_min
```

| Гейт | Что измеряет | Кто считает |
|---|---|---|
| `importance` | Насколько событие значимо | Downstream |
| `confidence` | Насколько мы уверены, что оно произошло | Downstream, по результатам проверки утверждений |
| `novelty` | Не писали ли мы это уже | Downstream, по истории публикаций |
| `actionability` | Можно ли на основании материала что-то сделать | Downstream |

**Конъюнкция, а не сумма.** Провал по любой оси означает, что материал не публикуется, независимо от значений остальных. Именно это свойство отсутствует у матрицы и именно поэтому она оставлена на приоритизации.

### 3.1. Что `URGENT` означает и чего не означает

| Означает | Не означает |
|---|---|
| Взять в проверку первым | Опубликовать |
| Разбудить редактора, если полоса не разгребается | Пропустить фактчекинг |
| Поднять частоту опроса смежных источников | Сократить требования к подтверждению |

Материал из `URGENT` с непройденным гейтом `confidence` не публикуется. Обратное — единственная ошибка, которую эта конструкция должна предотвращать, и ради неё она построена.

## 4. Состояния находки

```
NEW ──► SCORED ──► TRIAGED ──┬──► HANDED_OFF
                             └──► DROPPED
```

| Состояние | Значение |
|---|---|
| `NEW` | Найдено, стоп-правила ещё не применены |
| `SCORED` | Стоп-правила пройдены, баллы посчитаны |
| `TRIAGED` | Полоса присвоена, находка в очереди |
| `HANDED_OFF` | Передана downstream, дальнейшая судьба вне модуля |
| `DROPPED` | Отброшена: стоп-правилом, порогом `< 40` или истечением срока в `BACKLOG` |

Переход `DROPPED → SCORED` разрешён и является штатным: так работает подъём из `BACKLOG` при появлении подтверждения (см. [01-triage-scoring.md](01-triage-scoring.md) §5.2). Остальные обратные переходы запрещены.

## 5. Heartbeat наружу

Кроме потока находок модуль отдаёт heartbeat — ответы на десять вопросов ТЗ. Схема — [`schemas/heartbeat.schema.json`](../schemas/heartbeat.schema.json).

Пример ниже сокращён до двух ответов для читаемости; схема требует ровно десять — по одному на каждый вопрос, без пропусков. Вопрос, на который в этом тике нечего ответить, получает `"answer": "no"` или `"unknown"`, но не исчезает из отчёта.

```json
{
  "report_id": "hb_01J9XQ3P8N",
  "tick_at": "2026-08-27T09:15:00Z",
  "answers": [
    {
      "question_no": 1,
      "question": "Появилось ли что-то новое по Wildberries?",
      "answer": "yes",
      "data_age_seconds": 240,
      "hit_ids": ["hit_01J9XQ2M4K7T"],
      "note": "изменение тарифов хранения, вступает 3 сентября"
    },
    {
      "question_no": 4,
      "question": "Есть ли новые регуляторные или судебные риски?",
      "answer": "no",
      "data_age_seconds": 12600,
      "hit_ids": [],
      "note": "последний опрос класса D в 05:45, следующий в 10:45"
    }
  ],
  "urgent_count": 1,
  "queue_count": 0,
  "model_calls": 1
}
```

`data_age_seconds` обязателен у каждого ответа. Ответ «нет» без указания, насколько свежи данные, неотличим от «не проверяли» — и именно так теряются события, случившиеся в необследованном окне.

## 6. Что нужно построить дальше, чтобы модуль заработал

Карта — это правила и хранилище решений. Для работающего мониторинга не хватает:

| Слой | Состояние |
|---|---|
| Коллекторы источников (HTTP, diff снапшотов, Telegram) | Не входит в модуль |
| Реестр источников с тирами и рейтингом доверия | Не входит в модуль |
| Классификатор, проставляющий факторы матрицы | Не входит в модуль |
| Фактчекинг и четыре гейта | Не входит в модуль, интерфейс описан в §3 |
| Доставка редактору | Не входит в модуль |

Проработанная архитектура этих слоёв существует отдельно — `C:\Ведение группы в телеграм`. Общий словарь категорий (см. [00-monitoring-map.md](00-monitoring-map.md) §3) выбран именно для того, чтобы стыковка была возможна без переразметки накопленного.
